## 1. 核对范围与已确认口径

- “实验操作”按可发布、可被其他工作流引用的工作流（Workflow）实现，不再建立另一套定义模型。
- 忽略需求文档中已经删除的内容。
- Agent 和权限不在本轮范围内。
- “设备操作、集成操作、人工操作”等实验操作类别由领域包持有稳定身份，支持新增、改名、调整顺序和删除；工作流标签继续作为普通标签，不再兼任类别权威。
- 当前接口状态值 `source`、`published` 可分别显示为“草稿”“已验证”，本轮不另造一套状态值。
- 已发布工作流（Workflow）可作为子工作流（Subworkflow）使用；父工作流保存的是静态展开结果，运行时不再动态调用第二个工作流任务（WorkflowTask）。

## 3. OS 待开发项逐项确认

### OS-01 实验操作类型与列表筛选

| 项目 | 内容 |
|---|---|
| 文档需求 | 实验操作库支持按名称搜索，按类型、状态筛选；默认按设备操作、集成操作、人工操作分类展示；列表展示名称、类型和草稿/已验证状态。 |
| 当前实现 | 工作流定义包含 `workflow_type=normal\|subworkflow`，省略时默认 `normal`。类别接口提供设备操作、集成操作、人工操作三个默认类别，支持查、新增、改名、调整顺序和删除；类别写入唯一领域包的 `operation_categories.json`，不新增 SQLite 表。子工作流通过稳定的 `operation_category_uuid` 引用类别，类别改名不影响工作流。`GET /api/v1/workflows` 可按 `workflow_type`、`status`、名称和类别组合查询，省略新增条件仍返回全部。旧 `device_operation`、`integration_operation` / `integrated_operation`、`manual_operation` 标签仍能映射到默认类别。 |
| 前端接入 | 实验操作库先读取 `GET /api/v1/experiment-operation-categories`，再以 `workflow_type=subworkflow` 一次读取实验操作，并按返回的 `operation_category_uuid` 分组；只看单一类别时可追加同名查询参数。类别管理使用同一路径的 POST、PUT、DELETE。 |
| 删除规则 | 类别仍被任一子工作流引用时拒绝删除；先修改或清空这些子工作流的 `operation_category_uuid`，再删除类别。 |
| 验收条件 | 类别 CRUD、跨 OS 重启恢复、子工作流绑定与筛选、普通工作流拒绝挂类别、引用删除保护和旧标签兼容均通过公共 HTTP 回归。 |

确认：

- [x] 按上述范围开发
- [ ] 调整范围
- [ ] 本期不做

> 不会因为改名破坏工作流引用；旧类别标签继续兼容，但新写入以类别 UUID 为准。
