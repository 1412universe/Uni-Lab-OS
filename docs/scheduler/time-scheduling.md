# 时间排程：当前实现与使用边界

本文说明本轮代码实际提供的能力。工作区 `scheduler-design/ARCHITECTURE.md` 是完整目标设计；其中尚未接通的能力不能据此认为已经上线。

当前实现是**根据已知执行路径和节点耗时滚动生成时间计划，再由原执行内核检查并派发**。生产入口默认启用 CP-SAT，保留显式关闭开关。计划中的开始、结束时间是预测；到了预计结束时间，不会自动释放设备、样品或库位。

## 两个进程如何分工

分离部署仍然使用原来的两个进程：

| 进程 | 本轮职责 |
| --- | --- |
| 调度控制进程 | 管理 Task/Job 和工作流状态；解析当前参数；取得资源占用事实；估算时长；在后台线程运行 CP-SAT；验证候选；通过原检查流程提交派发和处理结果。 |
| 设备 Runtime 进程 | 接收原协议命令；检查开始许可；调用驱动；记录、上报真实结果；重连时重投已保存结果。 |

CP-SAT 是调度进程内的一个工作线程，没有新增第三个服务或 Gateway。求解线程只接收不可变快照，不操作设备、数据库或工作流状态。当前至多有一个求解任务和一个合并后的待处理快照。

候选计划通过版本检查和独立约束验证后，只决定当前就绪动作的顺序、建议设备和等待时间。派发前仍检查参数、依赖、运行模式、设备注册、库存、资源占用、Claim/Fence 和既有持久开始许可。求解失败、输入无效或只有旧版本候选时，等待并报告原因，不自动切回另一套排序算法。

## 算法实际优化什么

时间用向上取整的整数毫秒表示。模型包含节点前后依赖、明确允许的候选设备、设备/物料/库位冲突、实际在途动作，以及跨节点连续占用。

目标按顺序求解：先最小化最高有效优先级任务的目标完成时间之和，再处理较低优先级；随后缩短本轮整体结束时间，并减少相对上次计划的设备/时间变动。一个层级必须证明最优，才固定该结果并继续下一层。时间预算用完时，可以使用通过验证的可行候选；不能把 `FEASIBLE` 说成所有目标已最优。

有效优先级包含符合条件的等待时间提升。已经开始的动作不会被移动或打断。规模限额、未确定的分支和未知结束占用会缩小本轮范围，因此这不是对无限未来工作流的全局最优承诺。

完整路径已知时，目标是 Task 完成；路径未知时，优先安排产生下一项必要信息的前驱。例如先完成测量，再决定 if 分支。接口用 `completion_targets.kind=information` 标明这种目标，不能把它显示成整个任务的预计完成时间。范围受限时也会标记 `partial_tasks`。

## if、循环、人工确认和连续占用

| 情况 | 当前排程行为 |
| --- | --- |
| if 结果未知 | 先排产生条件输入的已知前驱；不猜选中分支，不把条件后继当作可执行动作。原工作流内核得出结果、激活实际分支后，重新生成计划。 |
| repeat_until 循环 | 只排已经物化的当前轮实例，不预先展开未知轮数。每轮由原内核判断退出或生成下一轮；循环尚未退出时，其后的节点不进入确定路径。 |
| 参数依赖上游结果 | 上游未产生所需值时，下游及依赖它的动作暂不进入模型；上游真实结果到达后重新解析和估时。当前没有自动对参数范围做场景预测。 |
| 人工确认 | 原流程仍可创建确认请求；不猜人的等待时长。等待中的后继不排，批准后真实动作仍须经过原检查；真实完成后才能继续后继。无资源冲突的独立任务可以继续。 |
| 跨节点连续占用 | 读取冻结资源计划和实际持有记录，分别表示直接使用和持续保管。释放动作已知时可预测区间末端；释放路径或时长未知时保持开放占用，竞争节点等待。区间内部合法动作仍可使用自身资源。 |
| 动作超过预计时间 | 有可用同组条件历史时更新剩余预测；否则标记 `actual_completion_overdue_unknown` 并保留占用。不冲突的任务仍可继续。 |

实际在途、外部未知占用和人工等待不会因退出本轮模型而消失。未知占用阻塞竞争节点及其依赖后继；本轮计划中的预测区间结束也不是物理释放事件。连续持锁跨越未决 if、循环或人工确认时，同样遵守这一规则。

## 耗时如何估计和学习

新入口是 `DurationEstimator.estimate_timing()`，返回固定结构 `TimingEstimate`，包含点估计 `point_s`、计划时长 `planned_s`、余量、来源、可信程度、样本数、规则版本、参数指纹、设备和计时边界。`planned_s=None` 表示未知，不能当作零耗时。

按以下顺序选择点估计：适用的公式及设备残差校准；参数声明的时长；同设备、同动作版本、同规则、同影响参数组的历史中位数；临时默认值。默认值和未独立验证的经验预测都标低可信。旧 `estimate()` 的全动作 EMA 接口继续兼容，但新排程不依赖缺少参数上下文的旧 EMA。

工程师通过 `feature_paths` 明确哪些参数影响耗时。不配置时使用全部参数隔离历史；空列表表示已经确认参数不影响耗时。系统当前不会自动筛选特征或训练机器学习模型。公式可体现圈数、转速等参数交互；历史分组不能自动推断没有样本的新参数组合。

例如，经设备语义确认后，恒速计圈动作可使用 `60 × cycles / rpm` 秒。该公式不猜测加减速是否计圈，不额外重复计算加减速；必须核实它是否适合该设备。各设备分别学习残差。只有明确验证残差可跨参数组共用时，才配置 `calibration_paths` 来放宽残差分组。

样本足够后，计划时长加入经验分位余量。公式使用残差分位，声明值或分组历史使用同组实际耗时分位；这仍是低可信经验值。调用方提供独立校准样本时可以使用校准误差分位，拟合数据更新会清除旧校准余量。默认分位是 0.9、最少样本数是 5，可通过 Python 构造参数调整；这些默认值不代表经过工艺验证。`hard_bound_s` 不据此生成。

当前自动采样边界是 `dispatch_to_observed_completion`，即调度器派发到观察到结果，不是设备 ACK，也不是已证实的物理起止。真实物理计时需要驱动另外提供事件证据。人工等待、非正常结束、需要核实的结果和恢复推断的起点不进入正常耗时训练。

生产桥在 `WorkflowStore` 复用的 SQLite 连接中建立 `scheduler_timing_observations`。首次正常成功结果与样本在同一事务提交，提交后才更新内存模型；同一 Job 重投结果时读取原样本，不按新的收包时间重新计时。启动时按提交顺序回放，跳过不兼容规则版本或计时边界。没有生产桥的独立构造只保留内存学习。原历史中缺少真实参数的数据不会被补猜后用于训练。

`estimate_remaining()` 接受已运行时间、可信进度或同组条件历史。样本不足时返回未知；不能简单将“原计划减去已运行时间”减成零并认定完成。适配层在原预计结束前保留初始结束预测，超过后才尝试条件剩余估计，始终保留真实派发起点。

## 配置和观测接口

`integration.setup_edge_scheduler()` 与 `main.build_scheduler()` 默认装配时间规划器。直接 `EdgeScheduler(...)` 不传 `time_planner` 时仍使用原排序；`TaskSchedulerBridge` 默认跟随所绑定调度器的模式，也可显式指定。这是兼容入口差异，不通过识别测试环境决定行为。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `UNILABOS_TIME_SCHEDULING_ENABLED` | `true` | `false` 或 `0` 关闭；`true` 或 `1` 开启。启动时生效。 |
| `UNILABOS_TIME_SCHEDULING_SOLVE_SECONDS` | `0.5` | 每次候选的总求解时间预算，单位秒。 |
| `UNILABOS_TIME_SCHEDULING_MAX_NODES` | `256` | 本轮模型节点规模限额。 |
| `ULAB_SCHEDULER_AGING_INTERVAL_SECONDS` | `30` | 符合条件的等待时间每累计多少秒提升一档有效优先级。 |
| `UNILABOS_TIMING_RULES_FILE` | 未设置 | 只读 JSON 文件路径；顶层是动作键到规则的映射。 |
| `ULAB_ESTIMATE_DEFAULT_S` | `60` | 缺少适用公式、声明和足够历史时的临时默认时长。 |
| `ULAB_ESTIMATE_MODE` | `auto` | 保留 `declared`、`historical`、`auto` 接口；新入口按参数分组，`declared` 模式不使用历史组。 |

以下仅为恒速计圈规则的配置示例，适用范围须由设备负责人验证；动作键必须与注册设备和动作一致：

```json
{
  "/devices/stir/run": {
    "version": "steady-count-v1",
    "feature_paths": ["cycles", "rpm"],
    "formula": "constant_speed_cycles",
    "timing_boundary": "dispatch_to_observed_completion"
  }
}
```

JSON 只允许内置公式名，不执行表达式。规则错误、重复键或非法数值会阻止加载；替换规则必须换版本。目前没有在线配置更新接口。生产开启时会实际导入 OR-Tools，部署前须检查它与 OpenCV、protobuf 等原生库在同进程中的兼容性，不能只检查包名或版本号。

本地 `edge` 镜像固定使用 `ortools==9.12.4544`，并将 `opencv-python-headless==4.11.0.86` 安装到独立 Python 搜索目录。这样避开 Conda 的 Python `cv2` 与 OR-Tools 之间的原生符号冲突，同时保留 ROS 图像桥依赖的 Conda C++ 库。镜像构建会以两种导入顺序验证真实 CP-SAT 求解和 ROS 图像往返；不应通过删掉 ROS 的原生库解决冲突。本地开发若复用 Conda OpenCV 环境，也需要相同的独立目录与 `PYTHONPATH` 配置。

- `GET /api/v1/scheduler/time-plan`：返回 `enabled`、`algorithm`、配置、最新候选、输入范围、阻塞原因和求解状态。`revision` 标识业务快照，`time_origin + start_ms / 1000` 才是绝对预测起点；`validated` 只证明候选符合本轮输入约束。
- `POST /api/v1/reschedule`：请求一次重排；不绕过开始检查。
- `GET /api/v1/timeline`：观察实际派发起点和当前估计。时间计划也包含在调度快照中。

关闭开关将同时回到既有排序和对应兼容恢复语义，不能把它当作运行中无影响的热切换。变更前应先排空或核实在途工作，再按部署流程重启。

## 重启、异常与尚未实现的部分

新模式下，设备 Runtime 身份变化后先恢复原结果路由，并把需要核实的执行和占用保留下来，不因重启伪造成功、失败或释放。设备已保存的真实结果按原身份重投；开始许可已使用但没有结果的动作不自动重做。只有持久证明 `NOT_STARTED` 的原命令可以重新经过开始检查。取消请求及原有期限继续保留。

普通重试还要求原尝试已明确结束、有完成记录且没有未解决的不确定性。结果不明时继续核实。工作流事实和库存 Claim 仍复用现有存储、投影及补偿流程；本轮没有把全部库存与执行事实改造成一个数据库事务。

以下目标尚未完整实现，不能宣称“覆盖了完整设计”或“全部释放入口均有物理证明”：

- 节点间最大衔接时限、关键资源时间窗的完整保障，以及设备 Runtime 保存、授权和执行限时动作段的协议没有接通。接口明确返回 `guaranteed_hard_time_limits=false`。统计分位和增加余量不等于硬时限保证。
- 未知 if 的多场景分支保护、未知循环轮数的前瞻展开、人工等待分布预测、未知参数范围的暂排尚未接入生产适配层。
- 当前按已确定的资源身份检查互斥和连续占用，尚未把设备与库位联合选择、可共享容量、物料数量和运行配额一起纳入时间优化。库存与这些执行条件仍由既有派发检查约束，候选计划本身不证明它们已得到完整保障。
- 等待时间提级目前只在调度进程内累计，尚未持久保存。调度进程重启后重新累计等待时间，不能保证重启前的提级结果继续保留。
- 自动特征学习、梯度提升分位模型、漂移检测、自动校准集划分和模型自动回滚尚未实现；当前使用公式、显式分组和经验统计。
- 旧普通异常仍可能触发全站暂停，尚未实现完整的局部异常隔离。旧人工处置入口和显式人工资源释放合同仍保留，不能说它们已经完成新设计要求的全部资源授权和物理结算校验。
- 不保证每次找到可行计划，也不保证有限模型的可行候选达到所有优先级目标的全局最优；状态、范围和已证明层级必须一起解释。

## 代码与验证入口

主要实现位于 `unilabos/app/scheduler/`：`workflow_planning.py` 提取当前可排路径，`time_scheduling.py` 对接执行事实，`time_planning.py` 建模和验证，`estimation.py`、`timing.py`、`timing_config.py`、`timing_store.py` 负责估时和样本。持久结果接入在 `workflow/task_scheduler_bridge.py` 与 `workflow/task_runtime_projection.py`。

独立验证脚本位于 `scripts/validation/`：`validate_time_plan.py` 与 `validate_time_scheduling.py` 使用隔离模型或记录执行器；`validate_time_scheduling_live.py` 验证在线纯软件工作流；`validate_time_scheduling_continuous_live.py` 验证 PLC-Sim 和软件机械臂上的连续持锁工作流。后两者需指向待验证服务。它们不替代真实设备工艺验证，也不据通过结果升级硬时限保证。
