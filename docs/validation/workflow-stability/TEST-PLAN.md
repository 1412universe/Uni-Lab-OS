# Uni-Lab-OS 全链路稳定性测试方案

状态：待执行方案；本文件不表示新增测试已通过。制定日期：2026-09-06。

目标是把工作流、调度和物料处理的稳定性落实为可重复验证的不变量、故障恢复行为和发布门槛。验收结论绑定代码版本、设备合同、部署配置及测试数据；任一关键绑定或配置改变，需要重跑相关验收。

## 1. 当前基线与验收范围

已有两轮核查的最后一次主回归为 **1137 passed、4 skipped**，并完成本地 Kubernetes `edge` PLC Sim 的 **6 次真实 OPC UA 命令、4 个任务成功**，SigNoz 有对应链路，任务结束后库存活动占用归零。证据见 [第二轮复审](../resource-locking-2026-09-06/review/README.md)。这是历史基线，执行本方案时必须在待发布版本重新生成结果。

现有 PLC 脚本通过 CallbackDispatcher 接真实调度器和持久库存，再访问模拟 PLC，**不能代替产品 API → 实际执行后端 → 驱动 → PLC 的完整验收**。完整装板、搬运、配平和工艺循环也尚未逐条做现场验收。

原有两项 `unlock_resources` 测试仍因恢复合同未明确而失败。本方案暂按“取得停止证据、必要时完成物料位置对账后再释放”编写恢复验收。操作员强制解除是否作为独立能力提供，是发布前必须关闭的决策项，不把未实现或失败测试算作通过。

## 2. 全链路边界

```text
工作流源码/编辑器
    → 保存、校验、发布、输入与实例绑定
    → 产品 HTTP API 创建任务（冻结快照、幂等键）
    → 编译后的 DAG、占用区间、整站静态无环验证
    → 物料准入、调度、库存 Claim/Fence 原子申请
    → 派发意图持久化、执行后端、真实使用的驱动
    → PLC Sim / 设备接受、执行、停止或完成证据
    → 回执接收、去重、物理位置/数量结算
    → 工作流状态、下一节点、部分资源释放
    → 任务终态、恢复状态、库存与镜像一致
    → API/UI 展示、事件投递、SigNoz 可追溯记录
```

逐跳检查，不能仅以最终任务显示 succeeded 判定成功。测试时使用部署实际选择的 simple/ROS 后端；若两种后端均作为受支持产品发布，则分别验收。

## 3. 必须始终成立的判定规则

| 编号 | 不变量 | 判断方法 |
|---|---|---|
| I01 | 同一独占资源没有相互冲突的实际执行者 | 用 PLC/Edge 命令执行日志重建时间区间，与库存 Claim、区间所有权比较；共同外层的不同设备并行不算冲突，同一设备命令仍不得重叠 |
| I02 | 每次只取得完整新增集合，失败不留下部分申请 | 任一成员冲突时检查全部新增 Lease/Fence；已有外层占用必须保持 |
| I03 | 实际使用资源均在冻结计划内，别名指向同一物理身份 | 比较输入、绑定、plan_id、派发资源和设备接收参数；绑定漂移必须重新验证或拒绝 |
| I04 | 同一执行效果不被重复执行/结算 | 按 task/job/attempt/effect UUID 核对接收与执行次数；重复网络投递可以存在，但物理执行和库存生效不能重复 |
| I05 | 一个物料身份只有一个已确认位置，一个单容量 Site 最多一个物料 | 结合 PLC Sim 独立位置模型、库存 Site、父子关系及物料身份检查；位置未知明确标记，不能同时宣称来源和目标均已确认 |
| I06 | pick 后物料在搬运器；place 确认后才到目标 | 取料前预留目标；每个搬运阶段断言来源、夹爪、目标和必要运动资源；失败不能伪造放料成功 |
| I07 | 数量不为负、不过量领取、重复回执不重复扣增 | 用独立账本检查期初 + 输入 = 期末 + 输出 + 明确损耗；统一单位，容差事先配置，未知量进入待对账而非强行平账 |
| I08 | 释放有实际停止/完成及物理交接依据 | 不依靠 timeout、预计时长、任务失败标志或 cancel 请求本身释放；物理责任未结束时持久保留并说明原因 |
| I09 | 已持久接受的任务和执行意图不会失踪 | 重启前后逐一追踪幂等键、effect、Claim、回执；对发送结果未知的请求禁止盲目重发不幂等动作 |
| I10 | 运行态、持久态、库存与展示最终一致 | 允许已定义的跨库投影短暂差异；按同一 effect/Fence 追踪，在规定恢复窗口内收敛，不能长期一边释放一边运行 |
| I11 | 无故障、前提持续满足的任务可推进 | 不死锁、不永久丢失唤醒；公平性在“无持续更高优先级无限流量、依赖和物料均满足”的条件下验证 |
| I12 | 结果不明和人工恢复有完整责任链 | 保留原任务、执行身份、物料、占用和原因；每次恢复命令可审计、可幂等重放，不以删除记录解决异常 |

实现一个独立检查器：从实际事件和快照重建这些不变量，不直接调用生产代码的“是否可释放/是否完成”辅助函数作为测试答案，避免同一个错误同时存在于实现和断言。

## 4. 环境、数据与执行约束

1. **固定版本**：记录 Git commit 加工作区 diff/hash、Python/mamba 环境、依赖版本、镜像摘要、数据库迁移版本、动作合同、设备绑定、调度容量与超时设置。
2. **本地基线**：使用 mamba `unilab` Python；现有 `edge` 的 PLC Sim 与 SigNoz 可供联调。测试 OS 使用专用配置、端口及独立工作流库/库存库，不复用日常任务数据。
3. **隔离故障测试**：为 PLC、Edge、Collector 等故障注入创建专用副本/测试实例。不要对共享 `edge` 服务直接重启、清库或注入延迟。共享模拟器上安排独占测试时段，同一工位只允许一个测试运行器控制。
4. **统一数据**：至少包括两个可独立工作的工位、机械臂、工具/导轨、来源库位、夹爪库位、目标及中间库位；材料包含唯一条码、相同模板不同实例、占用目标、空夹爪、夹爪持料及可分装数量。没有对应模拟能力的场景标记 blocked，不能改成假回执后仍标为 PLC 实测。
5. **独立物理证据**：模拟器应提供“命令接受/开始/完成/复位”序列日志或计数器，并能关联测试命令身份；位置和数量有独立状态。仅一个 completion=True 位不足以证明没有旧回执或重复执行。缺少这些能力时，先补模拟器观测接口。
6. **快照和时间**：性能时长用单调时钟；跨进程日志校时。正常结束在停止提交且队列排空后取一致快照；崩溃测试保留 WAL/事件序号，使用数据库支持的备份方式，不能直接复制正在写入的单个 SQLite 主文件作为完整证据。
7. **清理顺序**：先保存现场和运行不变量检查，再重置测试环境。不能在断言之前批量释放锁、清理残留任务或把未知物料改回来源。

## 5. 五层测试与执行顺序

| 层级 | 范围 | 运行时机 | 建议完成标准 |
|---|---|---|---|
| L1 合同与编译 | 源码、发布快照、输入、DAG、区间、绑定、静态环、Schema | 每次相关代码变更 | 对应需求和每个修复都有正反例；全量相关回归通过 |
| L2 持久化调度与库存 | 真实 SQLite、调度器、桥接、Claim/Fence、物料结算；可控执行边界 | 每次合并；夜间随机化 | 正常/异常用例通过；随机种子和反例可重放 |
| L3 产品全链路 | 实际产品进程、HTTP API、所用后端/驱动、PLC Sim、回执、API/UI、SigNoz | 夜间及候选版本 | 正常黄金流程连续 30 轮无非预期失败；注入场景得到准确预期终态 |
| L4 故障与持续运行 | 进程/网络/存储故障、回执乱序、并发压力、24/72 小时运行 | 候选版本 | 故障窗口全部覆盖；状态不变量零违规；资源和队列不持续增长 |
| L5 实际设备验收 | 生产实际驱动、传感器、夹爪/库位、装板及工艺 | 首次交付及驱动/物理合同变更 | 有界流程重复验证；停止证据和人工恢复演练通过，业务方签收 |

L1/L2 通过后才能开始对应 L3；L3 基本正常路径通过后才扩展故障和压力。故障注入先针对模拟器，真实设备只做经现场流程允许的停止与恢复演练。

## 6. 场景矩阵

可执行用例清单见 [CASES.csv](CASES.csv)。每行应实现为独立用例或参数化用例，并产生自己的 run_id、预期结果和证据。表中的“待自动化”代表本方案要求，不宣称现有 pytest 文件已完整覆盖。

### 6.1 工作流

- 从源码/编辑器保存发布，经真实 API 创建任务，完成输出与状态回读；发布后修改注册表不能改变已接受任务的合同。
- 串行、多层子流程、嵌套根/with、条件双分支、join、循环至少三轮、嵌套循环、循环外层范围；逐个改变完成顺序。
- 合法依赖下不误报环；二任务、三任务及并行真实环必须在物理派发前被拒绝。
- 输入为空、Schema 错误、动态资源未绑定、同实例别名、绑定变化、参数指向另一设备，均检查准确拒绝和零物理命令。
- 单步/暂停/继续/取消：暂停不凭空释放物理责任；进入取消不是设备已停止；任务终态后仍接收原在途作业的有效回执。

### 6.2 调度

- 同设备串行；不同设备在共同外层范围可并行；兄弟局部范围不得按 task_id 错误合并。
- 连续占用期间高优先级等待任务不能插入；结束后要唤醒等待者；公平性与优先级分别检查。
- 多资源竞争整组成功或整组失败；前驱持有 A+B 时后继只接管 A，B 仍保持；A 提前结束不能拖到 B 结束才释放。
- 跨任务容量上限、队列反压、过载恢复、同一工作流实例上限；验证不能突破实际设备并行上限。
- 共享范围重试的 Fence、陈旧 Fence、缺失区间投影、计划外派发、不可映射库存的资源，均不得绕过保护。

### 6.3 物料与业务流程

- 准入：现有物料、新建/自动供料、缺料等待、补料唤醒、同模板不同实例，不串料、不重复创建。
- 搬运：source→gripper→target；目标在 pick 前确定并预留；目标占用、夹爪已占用、来源变化时零部分执行。
- pick 成功后各边界故障、place 失败/跳过/取消，保留必要资源及真实位置；稳定中间 Site 后才允许交接。
- 原位处理必须确认物料仍在实际设备的正确 Site；分装检查批次、单位、数量、余量及损耗。
- 完整业务黄金流程：单板搬运处理回收；多样品并行；一组对位板；四板装入并处理；提前转位；拍照/刮板至卸板；机械臂/导轨跨 join。
- 配平、板型、允许站位等条件必须由具体设备合同定义，然后测试合法/非法组合，不能只以资源锁正确代表工艺合法。

## 7. 故障注入：必须覆盖的跨边界窗口

使用测试构建的确定性 failpoint/barrier，准确停在目标边界；不要靠随机 sleep 猜是否覆盖。生产默认关闭 failpoint。

| 窗口 | 注入 | 必须观察到的行为 |
|---|---|---|
| 接受任务已持久化、客户端尚未收到响应 | 断开客户端后用相同幂等键重试 | 返回同一任务，不创建第二条物理流程 |
| Inventory Permit prepared，工作流镜像尚未提交 | 终止测试 OS 进程 | 重启释放无物理责任的孤立 prepared，或安全复用；不得丢失已派发占用 |
| 派发意图已持久化、驱动发送之前 | 进程退出 | 恢复根据“确未发送”的证据推进；不能无声丢任务 |
| 驱动已发送、接受确认丢失 | 断链/终止 Edge | 标记结果未知并查询/对账；只有执行端持久幂等得到证明才可重投，不假定网络 exactly-once |
| pick 实际成功、位置回执尚未提交 | 丢回执/重启 | 不把物料错误保留在已确认来源或提前确认目标，载运资源不能放开 |
| place 实际成功、工作流结果尚未投影 | 重放回执、重启 | 位置与数量最多生效一次，恢复后正确推进 |
| 库存已结算、工作流镜像/前端事件未提交 | 进程退出 | 依据持久执行身份补投影，不能重新执行物理动作 |
| 两个共享分支交接/部分释放之间 | 同时回调、某一分支失败 | 不早放、不残留；不刷新另一在途分支 Fence |
| cancel 请求/接受/实际停止三者之间 | 超时、晚到成功或停止回执 | 请求/接受不等于停止；晚到有效结果能结算，冲突结果被隔离 |
| 事件写入后发送确认丢失 | 重放/乱序/重复 | 消费端幂等，审计保留，待发送积压可排空 |
| SigNoz/Collector 不可用 | 中断测试遥测接收 | 不以缺少 Trace 推断设备完成；调度安全不受影响，事件丢失/缓存策略符合明确合同 |
| 数据库忙、事务失败、磁盘不足 | 测试库故障 | 失败关闭，不先执行设备再发现无法持久化；恢复后不出现部分 Claim 或半次数量结算 |

每个关键窗口至少验证：单次故障、连续两次故障、同一效果回执重复 10 次、晚到回执、不同恢复顺序。模拟器中循环至少 20 次；随机状态机测试建议 100 个固定种子，每种子至少 1000 个事件，保存最小失败序列。

## 8. 压力、长稳与性能门槛

以下是首版候选门槛，属于**方案目标**，不是已测成绩；在固定机器/配置上测一次基线后，发布前冻结，不能在失败后临时放宽。

- **并发梯度**：1、5、10、25、50 个任务；在配置允许时增加到容量上限，并对超过上限的请求验证排队/拒绝和回落恢复。任务数不等于物理设备并发数。
- **负载组合**：均匀资源、80% 请求争抢同设备、双设备并行、长短任务混合、连续占用、物料短缺、任务取消和周期重启。
- **短压**：各梯度稳定运行 30 分钟；无故障阶段无非预期失败，无重复物理效果和不变量违规。
- **长稳**：先 24 小时通过，再候选版本连续 72 小时；模拟器累计至少 10,000 个 Job，设备速度导致数量不足则延长时长，不能通过伪造完成加速。
- **调度延迟**：从资源/依赖/物料全部就绪到持久化派发意图，建议 P95≤1秒、P99≤3秒；不把设备执行时长、缺料时间混入该指标。
- **恢复时限**：依赖恢复后，建议 60 秒内恢复对任务的可查询责任状态；5 分钟内排空可自动修复的投影/事件积压。物理结果未知只要求按时进入明确待对账状态，不要求强行完成任务。
- **容量与资源趋势**：暂停提交并排空后，活动 Job/Claim/Lease、待发送事件、连接及线程回到可解释基线。RSS 在相同负载窗口预热后不持续增长，首版阈值建议≤10%；必须同时查看样本趋势。审计表按任务量增长属于正常，不要求数据库文件恒定或自动缩小。
- **公平性**：有限固定集合、全部前置条件满足、无无限高优先级注入时，所有任务在队列排空前完成；另外测持续高优先级流量，明确是否提供老化策略及其配置，不能无条件承诺低优先级等待上限。

## 9. 证据、SigNoz 和失败定位

每轮建立唯一 run_id，并关联 workflow version、task_uuid、job_uuid、attempt、effect_uuid、claim_uuid、plan_id、material_uuid、Site、Fence 和 trace_id。高基数字段放 trace/log，指标使用受控维度。

每个场景产出：

```text
run-manifest.json      版本、镜像、绑定、数据库版本、测试配置、随机种子
case-results.json      每例预期结果、实际结果、失败或跳过原因
junit.xml              自动测试结果
physical-events.jsonl  独立命令接收/开始/完成/位置证据
invariant-results.json 各不变量的检查结果及最小违规现场
snapshots/             工作流库、库存库及必要日志的可恢复快照
traces.json            SigNoz 实际存储查询结果和关联身份
summary.md             通过/未通过/阻塞、性能统计与残留资源清单
```

SigNoz 应能按一块物料串起全流程，展示等待原因、取得与释放、命令及回执、位置提交、恢复命令。测试环境如要验收完整 trace，使用明确的全采样配置；抽样观测不能当作完整命令账本。

正常流程要求无非预期错误；故障注入允许与注入相符的错误 span，但必须有预期原因和恢复结果。不能要求故障测试也“错误 span 为零”。Collector 故障期间丢失 span 的合同应单独检验，业务恢复证据以持久事件/设备日志补全。

## 10. 发布判定

以下全部满足，才能给待发布版本签署“本验收范围内通过”：

1. 工作流、调度和物料的 P0 场景全部通过；不变量违规数为 0，非预期重复物理效果/库存结算为 0。
2. 所有必测场景有结果；blocked、未实现、未执行、失败不能折算通过。平台专用测试可在对应平台执行后单独汇总。
